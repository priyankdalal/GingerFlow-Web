Plugin development

Turn any Python capability
into a visual node.

A plugin is a ZIP archive containing a manifest and Python implementations. No C++ knowledge, no recompilation, no restart. New nodes appear in the Toolbox immediately after installation.

Package structure

my_plugin.zip
├── plugin.json          <- required manifest, MUST be at ZIP root
├── icons.json           <- optional icon map
├── nodes/
│   └── transform.py     <- Python implementations
└── requirements.txt     <- optional pip dependencies

Package the contents of the plugin directory, not the directory itself.

Compress-Archive -Path my_plugin\* -DestinationPath my_plugin.zip

Most common packaging error. If plugin.json ends up nested inside a folder in the archive, GingerFlow rejects the plugin. Verify the archive listing shows plugin.json with no path prefix.

Node function

A node implementation is a plain Python function. It receives the resolved inputs and configuration, and returns a dictionary keyed by output port name.

def run(inputs, config):
    text = inputs.get("text", "")
    mode = config.get("mode", "upper")

    if not isinstance(text, str):
        raise ValueError("text must be a string")

    result = text.upper() if mode == "upper" else text.lower()
    return {"result": result, "length": len(result)}

Raise an exception to fail the node. The message surfaces in the Output console and triggers the configured retry policy. Return only JSON-compatible values so results can cross the process boundary.

Data types

TypePython valueTypical use
stringstrText, paths, URLs, identifiers
numberint / floatCounts, amounts, thresholds
booleanboolFlags and branch conditions
objectdictStructured records and payloads
arraylistBatches, rows, collections
anyany JSON valuePass-through and generic utilities

Prefer paths over payloads for large data. Passing a file path between nodes keeps memory bounded; passing a multi-gigabyte value does not.

Config widgets

Config entries render as Inspector fields and arrive in the config dictionary. Common widget types include single-line text, multi-line text, number, checkbox, dropdown choice, file or directory pickers, and password fields for credentials.

Use config for settings that belong to the node instance, and inputs for values produced by upstream nodes.

Complete example

A minimal two-file plugin that adds one node.

plugin.json

{
  "name": "acme_text",
  "version": "1.0.0",
  "author": "Acme",
  "description": "Text utilities for GingerFlow",
  "nodes": [
    {
      "type": "acme_text.change_case",
      "display_name": "Change Case",
      "category": "Text",
      "description": "Convert text to upper or lower case",
      "entry": "nodes/change_case.py",
      "function": "run",
      "inputs": [
        { "name": "text", "type": "string", "required": true }
      ],
      "outputs": [
        { "name": "result", "type": "string" },
        { "name": "length", "type": "number" }
      ],
      "config": [
        {
          "name": "mode",
          "type": "choice",
          "label": "Mode",
          "options": ["upper", "lower"],
          "default": "upper"
        }
      ]
    }
  ]
}

nodes/change_case.py

def run(inputs, config):
    text = inputs.get("text", "")
    mode = config.get("mode", "upper")
    result = text.upper() if mode == "upper" else text.lower()
    return {"result": result, "length": len(result)}

Zip the contents, install through the Plugin Manager, and the Change Case node appears under the Text category.

Dependencies

List third-party packages in requirements.txt at the plugin root. GingerFlow installs them into the configured Python environment during installation.

requests>=2.31
python-dateutil>=2.9

Pin sensible version ranges so a future release cannot silently break your node, and prefer a dedicated virtual environment for experimental plugins.

Runtime model

Python nodes execute through a workflow-scoped, long-lived worker session that exchanges framed JSON requests and responses. That design keeps interpreter startup out of the per-node path and isolates plugin failures from the desktop process.

  • A node timeout of 0 is appropriate only for intentionally long-running listeners.
  • Workflow-level stop and cancel remain available even when a node has no deadline.
  • Register sockets, files, database handles, and subprocesses for cleanup so cancellation releases them.
  • A failed or timed-out Python process does not corrupt the desktop process.

Debugging

SymptomLikely cause
Plugin rejected on installplugin.json not at ZIP root, or invalid JSON.
Node missing from ToolboxDuplicate or malformed type, or a manifest node entry that failed validation.
Import error at run timeMissing dependency, or an entry path not relative to the plugin root.
Node returns nothingFunction returned a non-dictionary, or output keys do not match declared ports.
Node never finishesBlocking call with timeout set to 0 and no stop condition.

Use the Output console for tracebacks and bounded payload previews, and print diagnostics from your node while developing.

Security

Plugins are executable code. Installing one runs code through the configured Python runtime. Install only packages from sources you trust, review the Python files and requirements.txt, and check network calls, subprocess execution, credential handling, and file access before use.

Never hard-code secrets in plugin source or manifests. Read credentials from environment values or a secret store, and use least-privilege accounts for databases and APIs.

Packaging checklist

  • plugin.json is at the ZIP root and parses as UTF-8 JSON.
  • Every type is unique and namespaced by the plugin name.
  • Every entry path is relative to the plugin root and exists.
  • Declared outputs match the dictionary keys the function returns.
  • Dependencies are listed and version-pinned in requirements.txt.
  • Errors raise exceptions with actionable messages.
  • Long-running nodes have an explicit stop condition and cleanup.
  • No secrets are embedded in code, config defaults, or the manifest.
